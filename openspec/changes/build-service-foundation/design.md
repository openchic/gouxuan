## Context

服务基础从仅有健康接口及本地索引判断的骨架接入真实存储。当前已有数据库连接、Compose 和认证实现草稿，尚未完成完整基础设施验收。目录与技术选型遵循 [PLAN.md](../../../PLAN.md)，表的当前实施范围见 [DATABASE.md](../../../DATABASE.md)。

## Goals / Non-Goals

**Goals:** 建立真实持久化与私有存储，后续业务共用连接和迁移边界。

**Non-Goals:** 不创建业务表占位、不实现 worker、账号或检索工作流；生产 HTTPS 和恢复脚本归发布 change。

## Decisions

### 数据库与迁移

使用 Postgres / pgvector、SQLAlchemy 2.x 异步引擎及 psycopg 3，Alembic 管理扩展、表和索引。引擎与会话边界在 `app/database.py`，ORM 定义按实际使用进入 `models.py`。每次业务操作显式事务，不在网络或模型调用期间持有事务；不混用额外数据库连接池。

不单独部署向量数据库，避免业务版本与向量版本分开提交。v1 使用精确向量检索；实际索引表由资料 change 创建。

基础能力按实际消费者接入。当前登录功能先使用 Postgres 连接、Alembic 与认证三表迁移，不依赖对象存储或向量检索。pgvector 扩展在知识库实际接入时安装；私有存储在资料操作接入前验收。后续业务表随对应 change 开发时创建，基础 change 不预建业务表占位。

### 存储与启动

`app/objects.py` 对接私有 S3 兼容存储，只提供上传、授权服务端读取、对象确认和清理所需的少量操作，不建通用存储框架。开发 Compose 使用本地 S3 兼容存储及私有 bucket，生产连接由部署配置注入。

迁移作为一次性任务完成；API 启动检查目标迁移，不自动改表。`/healthz` 只检查存活，`/readyz` 基础部分检查数据库与迁移，独立报告存储状态。后续 worker 与问答状态由其真实模块加入；未实现的业务不报为 ready。

### 配置与接口

使用现有 Pydantic Settings 管理环境变量，连接与密钥不进入日志或 OpenAPI。开发基础设施先接入根 `dev:api`；资料及问答 worker 分别在对应 change 扩充编排，最终形成 PLAN 的完整入口。

## Risks / Trade-offs

- 数据库扩展与镜像不兼容 → 固定可安装 pgvector 的版本，验证全新数据库迁移。
- S3 兼容实现差异 → 用开发及目标存储验证私有权限、读写、失败与清理。
- 迁移失败导致启动竞态 → 迁移任务失败时阻断依赖进程，检查明确版本。

## Migration Plan

锁定依赖，替换本地索引文件配置，创建迁移与开发持久卷。验证新库、重复执行及错误版本的启动行为；回退前检查迁移是否涉及数据，后续业务迁移各自负责回退说明，不删除现有持久卷作为回退手段。
